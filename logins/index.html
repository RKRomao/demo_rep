O Que Acontece:

Ao submeter um formulário com método GET, o navegador lê os atributos name e value de cada campo de texto e concatena-os através de uma Query String separada por ? e &.

URL gerada: http://localhost:3000/api/login?username=anasilva&password=demo123!
❓

O Porquê Técnico:

A especificação original do protocolo HTTP/1.1 define que o método GET serve exclusivamente para solicitar representações de recursos e, por arquitetura, não contém corpo de mensagem (Request Body). Para enviar parâmetros num GET, o único local possível é a própria URL.

💡

Impacto & Boas Práticas:

Isto é excelente para filtros de pesquisa, mas arriscado para credenciais. Para registo e alteração de dados no SQL, deve usar-se sempre POST!

Arquitetura Web & Segurança

Porquê HTTP GET vs HTTP POST?

Compreenda a razão fundamental pela qual cada método foi criado no protocolo HTTP e onde cada um deve ser aplicado.

HTTP GET
"Busca de Informação"
  • Onde vão os dados? Na URL pública como Query String (ex: ?user=ana&token=123).
  • Tem Request Body? Não. Não transporta corpo de mensagem.
  • Idempotente & Seguro? Sim. Repetir o pedido GET não altera a base de dados SQL.
  • Cache & Histórico: Fica 100% memorizado no histórico do navegador e nas caches de proxies.
  • Quando utilizar? Pesquisas, paginação, filtros de produtos, carregamento de utilizadores.
HTTP POST
"Envio e Criação de Dados"
  • Onde vão os dados? No Request Body encriptado sob HTTPS, invisível na barra de endereços.
  • Tem Request Body? Sim. Suporta JSON, formulários codificados e upload de ficheiros binários.
  • Idempotente? Não. Executa INSERT ou UPDATE gerando novos registos no SQL.
  • Cache & Histórico: Nunca é memorizado na URL do histórico do navegador nem nos logs de servidores.
  • Quando utilizar? Registo de Utilizadores, Login Seguro, pagamentos, envio de formulários.
🎯

A Regra de Ouro do Protocolo HTTP:

Use GET quando a intenção for LER dados sem efeitos colaterais. Use POST quando a intenção for ENVIAR dados sensíveis ou ALTERAR a base de dados.
